# Core contracts and deterministic composition

The Rust core has no filesystem, AF runtime, subprocess, or model dependency. It receives typed values and returns validation diagnostics or deterministic Markdown. Storage and native review own source authority and publication.

`Record`, `Config`, and `State` use schema version 1. All structures reject unknown JSON fields, including nested sections, evidence, and provenance. Record input requires a version, kind, title, and body. The CLI allocates an omitted or empty ID before validation. Persisted IDs use 1–128 lowercase ASCII letters, digits, underscores, or hyphens. Revisions default to 1. Optional relationships, metadata, and sections default to empty; flags default to false. The JSON Schemas describe wire fields and scalar constraints; Rust additionally enforces relationships and semantic constraints.

The four kinds are `changelog`, `adr`, `docs`, and `performance`. Documentation alone may contain named sections. Only ADRs may be accepted. A performance record must include a typed `performance` object whose `type` is `policy` or `measurement`. Policy records contain a source inventory digest and rationale. Measurements contain that inventory digest and evidence with a repository-relative path, file digest, nonempty argument-vector command, and result digest. Digests use lowercase `sha256:` followed by 64 hexadecimal characters. Core validation checks the contract; the release boundary checks evidence bytes and inventory authority. Prose cannot establish measurement authority.

Baseline state retains every historical record in a map keyed by its ID and keeps a consumed-record digest map. Composition rejects any pending ID already present in either map, including byte-identical historical records. The storage boundary checks raw consumed bytes before release recovery. Records cannot be overwritten through composition.

A revision has its own ID, a `revises` predecessor, the same kind, and exactly the predecessor's revision plus one. A record without a predecessor has revision 1. Retirement requires a predecessor and non-whitespace rationale in the body. Revising an accepted ADR fails; a new ADR can instead explicitly `supersedes` the accepted decision and retain its history. All supersession preserves kind. Each pair of competing revisions needs a common explicit successor listing both branch IDs in `supersedes`; the core never chooses a branch silently.

Dependencies, revisions, and supersession form one directed acyclic graph. Unknown references, self-references, duplicate relationships, and cycles fail. Active records with unresolved `conflicts_with` relationships fail; superseded history remains available. Sections form their own directed acyclic graph through `after`, with unique section IDs and resolved references. Unknown section relationships and section cycles fail.

Rendering first validates the complete effective set. A sorted ready set produces topological ordering with lexicographic ID tie-breaking. Global ordering honors dependencies across kinds; a collection heading is emitted whenever the ordered kind changes. Section order uses the same algorithm. Arrival order cannot select output order. Lists of supersession links are sorted. Markdown keeps all record bodies, historical status and successor links, revision links, and performance authority fields. Stable anchors are `record:ID` and `section:RECORD-ID:SECTION-ID`; the core does not rewrite record prose.

`validate`, `render`, and `compose` receive `BTreeMap<String, Record>`. `compose` additionally receives `State`; `validate_config` checks source paths, schema version, and paired absolute adapter path/digest. `valid_id`, `valid_digest`, and `valid_relative_path` are shared boundary helpers. Source paths exclude empty segments, absolute roots, dot segments, backslashes, and NUL bytes.
